1. VISIÓN GENERAL
================================================================================

heyPudú! es una red social de audio breve. Los usuarios publican "briefcasts":
audios de máximo 5 minutos, con título, portada opcional y texto descriptivo
opcional. La red social es exclusivamente de audio: no se publican textos sin
audio. También pueden dar likes, comentar, seguir a otros usuarios y buscar
contenido.

El sistema está construido con una arquitectura de microservicios en Spring
Boot, desplegado en AWS, autenticado con AWS Cognito, y con un frontend en
React.

6. AUTENTICACIÓN Y ROLES (AWS COGNITO)
================================================================================

CONCEPTO CLAVE
--------------
TODOS los usuarios (normales y admins) existen en Cognito. No hay dos
sistemas de login. La diferencia está en los GRUPOS asignados.

User Pool: uno solo para toda la app.

GRUPOS
------
- user      -> ROLE_USER      (usuario normal)
- admin     -> ROLE_ADMIN     (administrador)
- internal  -> ROLE_INTERNAL  (futuro: cliente de servicio)

Los grupos viajan en el claim "cognito:groups" del JWT.

FLUJO DE REGISTRO
-----------------
1. Usuario se registra en Cognito con correo + contraseña (desde React con
   Amplify).
2. Cognito crea la cuenta, genera "sub" (UUID) y envía código de verificación.
3. Usuario verifica el correo.
4. Usuario inicia sesión y recibe un JWT con:
   - sub: UUID
   - email: correo
   - cognito:groups: ["user"]
5. React llama a POST /api/v1/auth/sync.
6. ms-auth guarda en auth_users: cognito_sub, email, status ACTIVE.
7. ms-auth llama a ms-users: POST /api/v1/internal/users con:
   - cognitoSub
   - name: "Usuario" (temporal)
   - username: "user_<primeros 8 chars del sub>" (temporal)
8. ms-users crea el perfil base.
9. React redirige a "completar perfil".
10. Usuario llama a PUT /api/v1/users/me con datos reales.

CREACIÓN DE ADMINS
------------------
No se puede crear un admin desde la página pública de registro.
Se crean manualmente:
- Consola de AWS Cognito
- AWS CLI (admin-create-user + admin-add-user-to-group)
- Script de seed en el backend

BANEO
-----
1. Admin llama a PUT /api/v1/admin/users/{id}/ban en ms-users.
2. ms-users cambia status a BANNED (NO elimina nada).
3. ms-users llama a ms-auth: PUT /api/v1/internal/users/{sub}/disable.
4. ms-auth llama a Cognito AdminDisableUser.
5. El usuario no puede volver a iniciar sesión.
6. Desbanear es reversible: PUT /unban + AdminEnableUser.

ELIMINACIÓN DE CUENTA
---------------------
1. Usuario llama a DELETE /api/v1/users/me en ms-users.
2. ms-users anonimiza: name="Usuario eliminado", username="deleted_<sub8>",
   bio=null, avatar_key=null.
3. ms-users cambia status a DELETED.
4. ms-users llama a ms-auth: DELETE /api/v1/internal/users/{sub}.
5. ms-auth llama a Cognito AdminDeleteUser.

DIFERENCIA BANEO vs ELIMINACIÓN
-------------------------------
- Banear: reversible, no borra datos, solo cambia status y deshabilita Cognito.
- Eliminar: irreversible, anonimiza datos y borra de Cognito.

REPORTES Y MODERACIÓN
---------------------
1. Usuario reporta una publicación: POST /api/v1/posts/{postId}/reports
   (ms-posts) o un comentario: POST /api/v1/comments/{commentId}/reports
   (ms-interactions).
2. El reporte se guarda con reporter_id (cognitoSub) y estado OPEN.
3. Un único índice parcial impide dos reportes OPEN del mismo usuario sobre
   el mismo elemento; si el anterior fue RESOLVED o DISMISSED puede reportar
   de nuevo y se conserva el historial completo.
4. El admin ve la cola en GET /api/v1/admin/posts/reports y
   GET /api/v1/admin/comment-reports.
5. El admin cambia el estado con PUT .../reports/{reportId}/{status}
   (RESOLVED o DISMISSED) y se guarda resolved_by.
6. Solo los reportes OPEN cuentan para los candidatos a baneo.

CANDIDATOS A BANEO
------------------
1. El frontend llama a GET /api/v1/admin/users/ban-candidates?threshold=10.
2. ms-users consulta a ms-posts /api/v1/internal/posts/reports/counts y a
   ms-interactions /api/v1/internal/comment-reports/counts.
3. Suma publicaciones y comentarios reportados por autor y devuelve los que
   superan el umbral, con el desglose de cada tipo.
4. Desde esa lista el admin puede banear o descartar al usuario.

8. ALMACENAMIENTO EN S3
================================================================================

BUCKETS
-------
- heypudu-audio   (audios de publicaciones)
- heypudu-covers  (portadas de publicaciones)
- heypudu-avatars (avatares de usuarios)

Todos privados. Solo accesibles con URLs prefirmadas.

FLUJO DE SUBIDA (audio/portada/avatar)
--------------------------------------
1. Frontend llama a POST /presigned-url con { fileName, contentType }.
2. Backend genera URL prefirmada de S3 (válida 15 min).
3. Frontend sube el archivo DIRECTO a S3 con PUT.
4. Frontend llama al endpoint de creación (post o perfil) con la key.
5. Backend guarda la key en la BD (NO la URL).

FLUJO DE LECTURA
----------------
1. Frontend pide un recurso (post, perfil).
2. Backend genera URL prefirmada de descarga (válida 60 min).
3. Frontend recibe la URL y reproduce/muestra el archivo.

REGLA CLAVE
-----------
La BD guarda KEYS, no URLs. Las URLs se generan en el momento.
Esto permite cambiar de proveedor de storage sin migrar datos.

VARIABLES DE ENTORNO (.env)
---------------------------
VITE_API_BASE_URL=http://localhost:3000/api
VITE_COGNITO_USER_POOL_ID=
VITE_COGNITO_CLIENT_ID=
VITE_AWS_REGION=

En producción VITE_API_BASE_URL apunta al API Gateway. Para probar cambios
locales contra la infraestructura real basta con poner la URL del API
Gateway y añadir http://localhost:5173 al CORS del API Gateway.

AUTENTICACIÓN CON AMPLIFY
-------------------------
- <Authenticator> de @aws-amplify/ui-react envuelve la app.
- Amplify.configure() con userPoolId, userPoolClientId, region.
- Token obtenido con fetchAuthSession().
- Se envía el ID token (session.tokens?.idToken), no el access token,
  porque el access token no incluye el claim email.
- Roles leídos desde cognito:groups del ID token.
- AuthContext expone cognitoSub (claim sub) para identificar al usuario en
  ms-posts y ms-interactions.

CLIENTE AXIOS
-------------
Un único cliente en src/api/httpClient.ts con baseURL = VITE_API_BASE_URL.
Interceptor que adjunta el JWT en cada request y normaliza los errores
(src/api/errors.ts) con el formato { path, error, message, status }.

GUARDS
------
- RequireAuth: redirige a login si no hay sesión.
- RequireRole("admin"): muestra 403 o redirige si no tiene el rol.

SUBIDA DE ARCHIVOS
------------------
Siempre vía URL prefirmada:
1. Pedir URL al backend.
2. Subir archivo directo a S3 con PUT.
3. Enviar la key al backend al crear/actualizar.

GRABACIÓN DE AUDIO
------------------
- MediaRecorder API del navegador.
- Requiere HTTPS en producción (o localhost en dev).
- Límite de 5 minutos.
- src/utils/audio.ts corrige la duración: los WebM de MediaRecorder
  reportan duration = Infinity, así que se hace seek a
  Number.MAX_SAFE_INTEGER y se lee la duración real.

REPRODUCCIÓN DE AUDIO
---------------------
- Reproductor persistente sobre la bottom bar (src/app/player.ts).
- Reproductor expandido con fondo derivado de la portada.
- La duración mostrada viene de audioDurationSeconds, no del elemento.

ACCIONES DEL FRONTEND
---------------------

- Ver y editar perfil propio, cambiar usuario y avatar.

11. DISEÑO VISUAL
================================================================================

PRINCIPIOS
----------
- Audio primero: reproductor siempre accesible.
- Poco texto, mucho gesto.
- Sensación de cercanía.
- Identidad propia por publicación.
- Móvil primero.

DEBE TENER

PRODUCCIÓN EN AWS (IMPLEMENTADO 2026-11-02)
------------------------------------------
- Cuenta AWS Academy (us-east-1). RDS está bloqueado por política, por lo
  que la base de datos es PostgreSQL administrado en Neon con SSL.
- Cinco microservicios en contenedores sobre una EC2 Amazon Linux 2023
  (t3.small, 2 GB) con swap de 2 GB y límites de memoria por contenedor.
- Las imágenes se construyen fuera de la EC2 y se publican en Docker Hub
  (unalmaermitana/heypudu-ms-*). La instancia solo hace `pull`.
- Application Load Balancer internet-facing con listener HTTPS (ACM) que
  enruta por path y puerto hacia cinco target groups (8081-8085). Los puertos
  de los servicios solo aceptan tráfico del Security Group del ALB.
- API Gateway HTTP API expone una única ruta `ANY /{proxy+}` hacia el ALB.
- Frontend en Vercel con VITE_API_BASE_URL apuntando a API Gateway.
- S3 con IAM Role en la instancia (LabInstanceRole) y CORS en los tres
  buckets (audio, covers, avatars).
- Detalle operativo completo en DESPLIEGUE-AWS.md.

API GATEWAY (RUTAS)
-------------------
Se usa una sola ruta comodín que conserva el path completo:

- ANY /{proxy+}  ->  http://<alb-dns>/{proxy}

El ALB decide el microservicio según reglas de path. Las rutas específicas
por servicio se descartaron: si comparten una única integración con prefijo
fijo, todas las peticiones terminan en el servicio equivocado.

Las llamadas entre microservicios NO pasan por el ALB: usan los nombres de
Docker (http://ms-users:8082, etc.).

IDENTIFICADOR DE USUARIO ENTRE SERVICIOS
----------------------------------------
- ms-auth, ms-posts y ms-interactions usan el `cognitoSub` del JWT.
- ms-users usa su `id` interno además del `cognitoSub`.
- ms-users expone endpoints internos `by-cognito/{cognitoSub}/...` para que
  ms-posts resuelva perfiles, seguidos y contadores sin ambigüedad.
- ms-users también consume ms-posts y ms-interactions (CLIENTS_POSTS_BASE_URL
  y CLIENTS_INTERACTIONS_BASE_URL) para calcular los candidatos a baneo.
- Las URLs prefirmadas nunca se almacenan en la base de datos.

15. REGLAS DE ORO
================================================================================

1. TODOS los usuarios existen en Cognito. No hay dos sistemas de login.
2. La diferencia admin/usuario está en los GRUPOS de Cognito.
3. La BD guarda KEYS de S3, no URLs. Las URLs prefirmadas caducan y no caben
   en columnas varchar(500).
4. Los archivos se suben DIRECTO a S3 con URLs prefirmadas.
5. Cada microservicio tiene su propia BD (esquema separado).
6. NUNCA acceder a la BD de otro microservicio.
7. Banear es reversible. Eliminar es irreversible con anonimización.
8. Los endpoints internos quedan abiertos en EP1 (trabajo futuro: token).
9. Los roles se leen del claim cognito:groups del JWT.
10. El frontend usa Amplify para Cognito y axios con interceptor.
11. Las URLs de microservicios se configuran por .env.
12. En producción, todas las URLs del front apuntan al API Gateway.
13. La BD guarda cognito_sub como clave externa.
    Entre microservicios el identificador es el cognitoSub; ms-users expone
    endpoints by-cognito para resolverlo.
14. El username se puede cambiar una vez cada 30 días.
15. Un usuario no puede seguirse a sí mismo.
16. Los endpoints internos van bajo /api/v1/internal/.
17. Flyway gestiona el esquema. Hibernate solo valida (ddl-auto: validate).
18. Nunca modificar una migración Flyway ya aplicada.
19. Nunca hardcodear credenciales de producción.
20. El frontend debe funcionar con el mismo backend que una app Android (API REST pura).
21. El frontend envía el ID token de Cognito (no el access token) porque es el
    único que incluye el claim email.
22. Un mismo usuario no puede tener dos reportes OPEN sobre el mismo elemento;
    el control es un índice único parcial, así que un reporte descartado se
    puede volver a emitir y el historial se conserva.
23. Solo los reportes OPEN cuentan para los candidatos a baneo.
24. Toda mutación de contadores (likes, comentarios, publicaciones) se
    notifica al servicio dueño del dato; nunca se escribe en su BD.

16. GLOSARIO
================================================================================

Briefcast:    Audio de máximo 5 minutos publicado por un usuario.
Cognito:      Servicio de AWS para autenticación de usuarios.
User Pool:    Almacén de usuarios en Cognito.
sub:          UUID único e inmutable que identifica a un usuario en Cognito.
JWT:          JSON Web Token, contiene identidad y grupos del usuario.
cognito:groups: Claim del JWT con los grupos del usuario.
ROLE_USER:    Autoridad de Spring para usuarios normales.
ROLE_ADMIN:   Autoridad de Spring para administradores.
ROLE_INTERNAL: Autoridad de Spring para clientes de servicio.
Prefirmada:   URL de S3 con permisos temporales para subir o descargar.
Presigned URL: URL prefirmada.
Soft delete:  Marcar como eliminado sin borrar físicamente.
Anonimizar:   Reemplazar datos personales por valores genéricos.
Reporte:      Señalización de un usuario sobre una publicación o comentario,
              con motivo y estado OPEN/RESOLVED/DISMISSED.
Candidato a baneo: Usuario cuyos reportes OPEN acumulados (publicaciones más
              comentarios) superan el umbral configurado (10 por defecto).
ID token:     Token de Cognito que incluye identidad completa (sub, email,
              cognito:groups). Es el que viaja al backend.
Access token: Token de Cognito con scopes; no incluye email, por eso no se usa.
URL prefirmada: Enlace temporal de S3 para subir o descargar un objeto.
Flyway:       Herramienta de migraciones versionadas de la base de datos.
Database-per-service: Cada microservicio tiene su propia BD.
BFF:          Backend For Frontend (capa que agrega llamadas).
Monorepo:     Un solo repositorio con varios microservicios.
