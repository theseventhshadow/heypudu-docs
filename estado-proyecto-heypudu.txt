1. DECISIONES DE ARQUITECTURA
================================================================================

DESPLIEGUE
----------
- El frontend React/Vite se despliega en Vercel.
- El backend corre en una EC2 con Docker Compose.
- Las imágenes se publican en Docker Hub y la EC2 solo hace `pull`.
- La base de datos es PostgreSQL administrado en Neon (schemas separados).
- La entrada pública es un API Gateway HTTP API que apunta a un ALB.
- Los microservicios no están expuestos directamente al navegador: sus puertos
  8081-8085 solo aceptan tráfico del Security Group del ALB.
- RabbitMQ se ejecuta en una EC2 separada con dos nodos Docker (`rabbit1` y
  `rabbit2`); la comunicación AMQP usa la red privada.
- Detalle completo en DESPLIEGUE-AWS.md.

AUTENTICACIÓN
-------------
- Se utilizará un único AWS Cognito User Pool.
- Los usuarios normales se registrarán desde el frontend.
- Los administradores no tendrán registro público.
- Los administradores se crearán mediante la consola de Cognito, AWS CLI o
  un proceso administrativo restringido.
- Los permisos se determinarán mediante grupos de Cognito:
  - user     -> ROLE_USER
  - admin    -> ROLE_ADMIN
  - internal -> ROLE_INTERNAL (futuro).

ALMACENAMIENTO
--------------
- Los archivos se almacenan en S3.
- Los buckets deben permanecer privados.
- El frontend sube archivos directamente a S3 utilizando URLs prefirmadas.
- La base de datos almacena keys de S3, nunca URLs permanentes.

MICROSERVICIOS
--------------
- Cada microservicio mantiene su propio esquema de base de datos.
- Ningún microservicio accede directamente a la base de datos de otro.
- La comunicación síncrona entre microservicios se realiza mediante REST y la
  comunicación asíncrona de comandos/eventos mediante RabbitMQ.
- Los endpoints internos utilizan el prefijo /api/v1/internal/.
- El identificador entre microservicios es el `cognitoSub` del JWT; `ms-users`
  expone endpoints `by-cognito/...` para resolver desde ese valor.

5. CRITERIO PARA MARCAR UNA TAREA COMO HECHA
================================================================================

Una tarea solo debe pasar de POR HACER a HECHO cuando:

- La implementación existe en el código o infraestructura correspondiente.
- La funcionalidad fue validada con una prueba o verificación concreta.
- La documentación relacionada fue actualizada, si corresponde.
- No depende de una configuración pendiente que impida utilizarla.

Al completar una tarea:

1. Cambiar [POR HACER] por [HECHO].
2. Moverla a la sección correspondiente de HECHO si ya no necesita seguimiento.
3. Agregar una nota breve con archivos, endpoint o configuración involucrada.
4. Registrar cualquier limitación que permanezca pendiente.
